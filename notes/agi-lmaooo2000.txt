3\. What to build before graph engineer (ordered)



Think in layers of trust, bottom → top.



Layer A — Inventory \& sockets (so the map can match reality)



1\. Capability/block registry extension

&#x20;  Closed kinds: software | connector | skill | prompt | mcp | external\_mcp | human | research

&#x20;  Each row: id, status (draft|sandboxed|verified|revoked), entrypoint, requires, oracle, provenance, last\_smoke\_at, risk\_class.



2\. Role sockets (“empty blocks”)

&#x20;  e.g. executor.pre\_task\_skills\[], manager.blocker\_skill, goal.policy\_skill

&#x20;  Only verified (or sandboxed-allowlisted) skills/prompts attach.

&#x20;  Without sockets, graph engineer has nowhere truthful to “plug in.”



3\. create-prompt factory (thin)

&#x20;  Input: role + mission slice + examples → draft prompt → static checks (secrets patterns, disallowed tools, length) → human or critic pass → versioned file under prompts/ or registry.

&#x20;  Parallel to create-skill, not a free monologue.



4\. create-skill → promote pipeline

&#x20;  create-skill → sandbox run on fixture tasks → (optional) external/static critic → mission/constitution checklist → promote to verified + attach to socket.

&#x20;  Alternate path you mentioned: always sandbox first; never write straight into production sockets. Prefer that as default.



Layer B — Same factory discipline for MCP \& workflows



5\. MCP factory beyond wrap

&#x20;  v0 wrap is “hello world.” Need: versioning, revoke, re-smoke on capability change, real invoke oracle, no silent registry invent.



6\. Workflow-from-graph factory (pre–graph-engineer)

&#x20;  Process you described is exactly right:



draft graph → graph critique (structure, missing oracles, cycles, risk)

&#x20;       → freeze graph version

&#x20;       → resolve/fill nodes (only verified blocks or enqueue factories)

&#x20;       → per-node smoke

&#x20;       → whole-graph smoke (cheap path)

&#x20;       → goal run under budget

&#x20;       → oracles + traces + weights



&#x20;  Graph engineer later only authors/revises graphs into that same pipeline; it does not skip it.



Layer C — External world (harder; after A–B)



7\. Ingest pipeline for external assets

&#x20;  GitHub skill / MCP / repo / raw file:



find → fetch (pinned commit/hash) → static scan → malware/secrets heuristics

&#x20;       → license/provenance → sandbox execute (if runnable)

&#x20;       → rank (usefulness vs risk) → human gate (later: push)

&#x20;       → registry as external\_\* draft → promote after smoke



&#x20;  Without pin + hash + revoke, external is a supply-chain time bomb.



8\. Human approval channel (defer, but design the hook now)

&#x20;  Interface only: needs\_human\_approval(action, risk\_class) → block until receipt.

&#x20;  Later: push + “mute for N requests / D days / action\_class.”

&#x20;  Do not build notifications before the approval state machine exists on disk.



Layer D — Learning loop (parallel, lightweight)



9\. Unified outcome schema

&#x20;  Extend goal\_trace (or sibling):

&#x20;  outcome ∈ {proven, failed, deeper, revoked, human\_rejected} + failure\_class + train\_weight.

&#x20;  Skills/prompts/MCP/workflow all emit the same family so FT doesn’t only learn “write code.”



10\. Never train on unverified external success as high weight until sandboxed-proven.

4\. Your proposed order for graph/workflow (correct)



Yes:



1\. Evaluate knowledge graph / workflow graph first (structure + oracles + risk).

2\. Then fill lego blocks (or enqueue software/MCP/skill factories).

3\. Then node QC + graph smoke.

4\. Then full goal under budget.

5\. Along the way traces weighted by outcome.



That is the same spirit as: master plan → phases → field\_tests → field\_proven, just for composition.
